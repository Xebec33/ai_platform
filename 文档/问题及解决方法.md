# 问题及解决方法

- **Vue 模板格式冲突**：Prettier 与 ESLint Vue 排版规则冲突。关闭冲突规则，保留逻辑检查。
- **DSL 类型错误**：JSON 索引签名不兼容可选字段。允许索引值为 `undefined`。
- **Shell 写入异常**：引号、`$schema`、`$id` 被 Shell 展开。改用分块安全写入并格式化校验。
- **函数重复定义**：分块追加导致函数重复。删除重复实现后重新检查类型。
- **Vue Flow 节点边框、连线和文字样式丢失**：前端全局样式重构时误删了 `.flow-panel`、`.vue-flow__edge-path`、`.workflow-node`、`.workflow-handle` 等关键样式，同时入口文件未加载 Vue Flow 的基础样式，导致节点只剩无框文字、连线不可见或文字布局异常。恢复 `@vue-flow/core/dist/style.css` 与 `@vue-flow/core/dist/theme-default.css` 的导入，并在 `前端/src/styles.css` 中补齐画布、边、节点容器、Handle、分支标签和文本溢出规则；节点描述改为明确的中文文案并为长文本增加 `title` 提示。通过前端构建和测试验证。
- **沙箱 /tmp 写满导致 Sandbox 执行失败**：coding-agent 在沙箱内执行 `npm install`，npm 缓存默认写入 `/tmp`（沙箱内 HOME=/tmp），把 64M 的 /tmp tmpfs 写满，opencode 的 SQLite 会话库写入报 `Failed to execute statement`，错误被稀释后前端只显示笼统的「Sandbox 执行失败」。修复：Docker 沙箱为 /tmp 单独挂载 512M tmpfs，并为 npm 缓存独立挂载 `/var/cache/npm`（512M）+ 注入 `npm_config_cache=/var/cache/npm`，实现 npm 缓存与 opencode 存储隔离；同时失败信息透传 `exitCode` 与 stderr 尾部，便于定位。
- **沙箱容器 OOM（exitCode=137）**：/tmp 写满修复后 npm install 可以执行，但 1024M 容器内存无法同时容纳 npm 与 opencode 进程，cgroup OOM 杀掉进程（dmesg 可见 oom-kill）。修复：`SANDBOX_MEMORY_MB` 提升至 1536（宿主机总内存 3.6G）。
- **自举开发后前端白屏**：自举 workspace 内 coding agent 自行执行 vite build 时使用了默认 base=/，产出的 index.html 引用根路径资源；同时 dist/ 被 gitignore，新哈希 JS 文件未进入 git——merge 提交后仓库中的 index.html 指向不存在的文件，页面 404 白屏。修复：建立「合并后自动部署」管线（orchestrator `onMerged` 回调 → app.ts detached spawn `scripts/deploy-after-merge.sh` → flock 串行 → 按改动范围重建前端双 bundle 或后端 → `git add -f` dist 产物提交 → pm2 restart）。平台权威重建，不信任 agent 产物。
- **自举会话详情加载极慢（3.5~8MB 响应）**：Run 原始结果包含 checkpoints（1.2M）、nodeRuns 节点 input 链式放大（2.4M）、variables（300K）与 coding-agent rawOutput，全部经 HTTP 下发，公网加载详情页 9 秒以上。修复：HTTP 边界统一过 `compactRunResult`（后端/src/self-development/compact.ts）——剔除 checkpoints/variables/节点 input/rawOutput，events 只保留渲染所需字段并截断，效果 3.5MB→12.5KB；完整数据保留在内存与 result.json。
- **自举合并被拒（BASE_WORKTREE_DIRTY）**：服务器主仓库被 dist 漂移、误跟踪的运行时文件（后端/data、后端/input）与测试残留弄脏，merge 前置检查拒绝。修复：运行时数据一律 untrack 并加入 .gitignore，后端启动时自动补种 demo 输入文件，服务器仓库保持 clean 的纪律见部署文档。
- **本地与生产 worker 抢同一队列**：本地 dev 的 .env DATABASE_URL 指向云上 PostgreSQL，本地 worker 与生产 pm2 worker 消费同一个 workflow_jobs 队列，出现「本地改动不生效」的假象（任务被另一侧旧代码认领）。排查：`pg_stat_activity` 看 client_addr。纪律：改后端执行逻辑先部署生产再验证。
- **Agent 输出无法解析为结构化 JSON（根因：maxTokens 过小 + 推理模型）**：demo 工作流载入编辑器时被盖默认 `maxTokens: 2048`，而 deepseek-chat 为推理型模型，思考 token 与正文共享 2048 预算；推理一旦超限，content 为空或 JSON 被拦腰截断（`finish_reason=length`）。此前 Provider 丢弃 finish_reason，空内容静默变成「无法解析为 JSON」，完全不可定位，表现为高概率而非必现（推理长度波动 108~12670 tokens）。修复三层：Provider 捕获并透传 `finish_reason`；executor 遇 `finish_reason=length` 直接报可操作错误 `LLM_OUTPUT_TRUNCATED`（含 maxTokens 值与建议，不做注定失败的重复请求）；编辑器 Agent 默认 maxTokens 2048→8192。另为一般解析失败增加一次纠正重试（附纠正提示词）并在最终错误中附原始输出摘要。
- **Loop Engineering demo 载入编辑器后点运行无反应**：前端编辑器给 Loop 节点盖默认 `timeout: 0`（UI 标注「0 为不限制」），但共享类型 `validateWorkflow` 要求 loop 的 timeout 若存在必须为正数——图转回 DSL 后 timeout:0 原样带入，后端 400 拒绝，而前端错误提示只有一句笼统的「Workflow 校验失败」。且 runtime 对 `timeout: 0` 语义是立即超时（`elapsed >= 0` 恒真），0 在运行层同样危险。修复：`uiGraphToWorkflow` 转换层把 loop 的 `timeout <= 0` 归一为 undefined（不限制），校验规则保持严格；同时 `runWorkflow` 前端 API 在 400 时把后端 issues 明细拼进错误信息，避免只显示笼统提示。
