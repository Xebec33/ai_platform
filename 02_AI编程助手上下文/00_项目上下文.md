# AI 工作流平台项目上下文

## 1. 项目简介

本项目是一套支持多 Agent 编排和 Loop Engineering 的 AI 工作流平台。

项目的核心目标不是简单实现一个聊天机器人，而是构建一个能够：

* 可视化编排多个 Agent；
* 定义复杂 AI Workflow；
* 执行顺序、条件、并行和循环逻辑；
* 持久化 Workflow Run 和执行状态；
* 支持 Agent、Tool、Coding Agent；
* 对失败任务进行自动观察、验证、修复和重新执行；
* 最终利用自身的 Agent 工作流完成平台自身开发；

的 AI Agent Workflow Platform。

项目最终需要完成两个层次。

### 基础要求

实现一套支持 Multi-Agent Orchestration 和 Loop Engineering 的 AI 工作流平台。

### 进阶要求

基于该平台搭建一套能够自举开发平台自身的工作流。

即：

> Platform → Workflow → Coding Agent → Test → Review → Fix → Platform Evolution

## 2. 项目核心理念

本项目遵循以下原则：

### 2.1 Workflow 是一等公民

Workflow Definition、Workflow Run、Execution State 必须明确分离。

不要把一个 Workflow 的定义和某一次执行混在一起。

### 2.2 Agent 不负责控制整个 Workflow

Agent 负责：

* 推理；
* 规划；
* 任务拆解；
* 代码生成；
* 代码修改；
* Review；
* 根据上下文进行决策。

Workflow Runtime 负责：

* 节点调度；
* 顺序执行；
* 条件分支；
* 并行；
* Loop；
* Retry；
* Timeout；
* State Persistence；
* Cancellation。

不要依赖 LLM Prompt 来实现确定性的流程控制。

### 2.3 Loop Engineering 是核心能力

Loop 不只是：

```text
失败 → 重试
```

而应该形成：

```text
Trigger
↓
Load State
↓
Execute
↓
Observe
↓
Verify
↓
Decide
↓
Continue / Stop
↓
Persist State
↓
Execute again
```

Loop 必须支持：

* iteration；
* maxIterations；
* stop condition；
* retry；
* timeout；
* failure handling；
* cancellation；
* persistent state。

### 2.4 小步实现，持续验证

项目开发过程中不得一次性实现全部功能。

每一个阶段都必须：

```text
理解
→ 设计
→ 实现
→ TypeScript 检查
→ 测试
→ 手动验证
→ 修复
→ 提交 Git
```

只有通过当前阶段验收后，才进入下一阶段。

## 4. 技术栈

### Frontend

* Vue 3
* TypeScript
* Vite
* Vue Flow
* Pinia
* Element Plus 或 Naive UI

### Backend

* Node.js
* TypeScript
* Fastify 或 Express

### Workflow Runtime

使用 LangGraph.js。

核心思路：

```text
自定义 Workflow DSL
        ↓
Compiler
        ↓
LangGraph StateGraph
        ↓
Runtime
```

### Database

PostgreSQL。

用于持久化：

* Workflow；
* Workflow Run；
* Node Run；
* Execution State；
* Checkpoint。

### Queue

Redis + BullMQ。

用于：

* 异步 Workflow；
* Worker；
* Retry；
* Timeout；
* 并发控制。

### Coding Agent

通过 Adapter 接入：

* OpenHands；
* 或 OpenCode。

Coding Agent 不应直接成为系统核心 Runtime，而应该作为一种 Agent Executor / Tool 能力存在。

### Sandbox

Docker Sandbox。

用于隔离 Coding Agent 的代码执行环境。

## 6. 核心 Workflow Node

第一阶段只实现：

* Start
* Agent
* Condition
* End

* Parallel
* Loop
* Tool

后续可以增加：

* HTTP Request
* File Read
* File Write
* Shell
* Git
* Code Execution
* Search
* Human Approval
* Delay

不要一开始实现大量 Node。

## 7. 多 Agent 模式

平台至少需要能够表达：

### Sequential

```text
Agent A
↓
Agent B
↓
Agent C
```

### Parallel

```text
       ┌→ Agent A ─┐
Start ─┤→ Agent B ─┼→ Merge
       └→ Agent C ─┘
```

### Conditional Routing

```text
Agent
 ↓
Condition
 ├─ Yes → Agent A
 └─ No  → Agent B
```

### Review Loop

```text
Coder
 ↓
Test
 ↓
Reviewer
 ↓
Pass?
 ├─ Yes → End
 └─ No  → Fix
           ↓
          Test
```

## 9. AI IDE 的角色

AI IDE 是项目的主要编码执行者。

AI IDE 可以：

* 阅读代码；
* 阅读项目上下文；
* 阅读参考项目；
* 分析架构；
* 设计实现方案；
* 修改代码；
* 创建文件；
* 编写测试；
* 运行命令；
* Debug；
* 分析 Git Diff；
* 修改 Bug；
* 编写文档。

用户负责：

* 产品决策；
* 架构最终决策；
* 阶段验收；
* 测试结果确认；
* 是否进入下一阶段；
* 是否接受重大架构变化。

AI IDE 不应该自行决定重大架构变化。

## 11. 代码修改原则

任何修改必须尽量：

* 局部；
* 可测试；
* 可回滚；
* 符合现有架构。

禁止为了完成单个功能而：

* 随意更换技术栈；
* 删除核心模块；
* 绕过类型检查；
* 删除测试；
* 引入无必要的大型依赖；
* 进行无关的大规模重构。

如果发现架构存在明显问题，应先提出方案，而不是直接推翻现有架构。

---

## 12. 项目完成标准

项目完成不是“代码能够运行”。

至少需要：

1. Workflow 可以可视化编辑；
2. Workflow 可以保存和加载；
3. Workflow DSL 可以校验；
4. DSL 可以编译为 LangGraph；
5. Multi-Agent Workflow 可以运行；
6. Condition / Parallel / Loop 可以运行；
7. Run State 可以持久化；
8. Workflow 可以监控；
9. Agent 可以调用 Tool；
10. Coding Agent 可以修改代码；
11. Coding Agent 在 Sandbox 中运行；
12. Self-Development Workflow 可以运行；
13. Loop 可以自动发现失败并修复；
14. 最终可以完成一次完整的自举开发 Demo。

---

## 13. AI IDE 开发时的优先级

如果不同需求发生冲突，优先级如下：

```text
正确性
>
架构一致性
>
可测试性
>
可维护性
>
功能数量
>
代码简洁程度
>
性能优化
```

不要为了增加功能数量而牺牲核心 Runtime 的稳定性。
