# AI 编程助手开发规则

## 1. 总原则

你是本项目的主要编码执行者。

你的职责是：

```text
理解需求
→ 理解现有代码
→ 分析架构
→ 制定方案
→ 实现
→ 测试
→ 修复
→ 汇报
```

不要只负责“写代码”。

---

## 2. 修改代码前

任何非 trivial 修改，都必须先：

1. 阅读相关文件；
2. 搜索相关代码；
3. 理解调用关系；
4. 理解现有数据结构；
5. 判断是否影响其他模块；
6. 制定实现方案。

禁止：

```text
看到需求
↓
直接创建新文件
```

---

## 3. 修改后的验证

修改完成后至少执行：

```text
TypeScript 类型检查
↓
Lint
↓
相关 Unit Test
↓
相关 Integration Test
```

如果条件允许，再进行：

```text
Manual Test
```

---

## 4. 测试失败

如果测试失败：

```text
失败
 ↓
阅读错误
 ↓
定位根因
 ↓
修改代码
 ↓
重新测试
```

不要：

* 删除测试；
* 降低测试标准；
* 注释掉失败代码；
* 捕获异常后静默忽略；
* 修改测试来掩盖实现问题。

如果确认测试本身存在问题，可以提出修改测试的理由。

---

## 5. 架构边界

不得未经批准：

* 更换技术栈；
* 更换数据库；
* 删除 LangGraph；
* 删除 Workflow DSL；
* 删除 Runtime；
* 用 Dify Backend 替代 Backend；
* 改成 Python Backend；
* 删除 Loop Engineering；
* 将 Coding Agent 与 Runtime 强耦合。

---

## 6. 不要过度设计

优先：

```text
简单
稳定
可测试
可扩展
```

不要为了理论上的未来需求：

* 创建大量抽象层；
* 创建复杂插件系统；
* 引入过多依赖；
* 创建不必要的微服务；
* 实现暂时不用的功能。

---

## 7. Node 开发原则

新增 Node 时必须明确：

```text
Node Type
Config
Input
Output
Execution
Error
Timeout
```

并至少拥有对应测试。

---

## 8. Agent 开发原则

Agent 必须尽可能：

* 输入明确；
* 输出结构化；
* 错误可识别；
* 不直接控制 Runtime；
* 不直接修改全局状态。

---

## 9. Tool 开发原则

Tool 必须：

* 有明确 Schema；
* 有权限边界；
* 有 timeout；
* 有错误处理；
* 可测试。

---

## 10. Coding Agent 原则

Coding Agent：

* 必须阅读项目上下文；
* 必须阅读相关代码；
* 必须查看 Git Diff；
* 必须运行相关测试；
* 不允许直接访问生产环境；
* 不允许无约束执行宿主机命令。

---

## 11. 文件修改原则

优先修改现有代码。

只有在必要时创建新文件。

避免：

```text
为了一个很小的功能
→ 创建十几个文件
```

文件结构必须服务于模块边界，而不是追求文件数量。

---

## 12. 重构原则

如果当前任务不需要重构，不进行大规模重构。

如果发现明显架构问题：

```text
发现问题
 ↓
分析影响
 ↓
提出方案
 ↓
等待确认
```

而不是直接重构整个项目。

---

## 13. Git 原则

每完成一个稳定阶段，应提交 Git。

推荐：

```text
feat: implement workflow DSL
feat: add condition node
feat: add loop runtime
feat: add run persistence
feat: add coding agent adapter
feat: implement self-development workflow
```

不要把大量不相关修改堆到一个 Commit。

---

## 14. 上下文原则

项目开发前优先读取：

```text
PROJECT_CONTEXT.md
```

根据任务读取：

```text
02_AI编程助手上下文/
```

如果需要详细技术设计，再阅读：

```text
文档/
```

不要每次无差别读取所有项目文件。

---

## 15. 开源代码使用原则

允许参考：

* LangGraph；
* Dify；
* Paperclip；
* Multica；
* OpenHands；
* OpenCode。

但必须明确：

```text
参考
≠
复制整个项目
```

优先理解其：

* Architecture；
* Data Model；
* Workflow；
* Agent；
* Task；
* Runtime；

再实现本项目需要的部分。

---

## 16. 重大决策

以下变化必须先提出：

* 技术栈；
* 数据库；
* Workflow DSL；
* Runtime；
* Agent 架构；
* Queue 架构；
* Sandbox 架构；
* 项目目录结构。

需要说明：

```text
问题
→ 方案 A
→ 方案 B
→ 推荐方案
→ 影响
```

等待用户决定。

---

## 17. 开发汇报格式

每完成一个任务后，简要汇报：

```text
## 完成内容

- ...
- ...

## 修改文件

- ...
- ...

## 测试

- TypeScript: PASS
- Lint: PASS
- Unit Test: PASS
- Integration Test: PASS

## 遇到的问题

- ...

## 当前限制

- ...

## 下一步

- ...
```

不要只说：

```text
Done.
```

---

## 18. 最重要的原则

始终遵守：

> **代码能够运行 ≠ 功能完成。**

必须同时满足：

```text
实现
+
类型检查
+
测试
+
手动验证
+
架构一致
```

才能认为一个阶段完成。
