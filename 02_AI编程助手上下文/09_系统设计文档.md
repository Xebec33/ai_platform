# 系统设计文档

> 本文档描述 AI Workflow Platform 的实际系统设计。架构决策、模块边界与运行机制以本文档为准；开发规范见 [06_开发规则.md](06_开发规则.md)，测试规范见 [07_测试规范.md](07_测试规范.md)。

## 1. 系统概述

AI Workflow Platform 是一套支持多 Agent 编排与 Loop Engineering 的工作流平台，并提供一条**自举开发（Self-Development）**工作流——平台通过自身的 Agent 工作流完成对平台自身源码的需求分析、编码、测试、审查、修复与合并。

核心能力：

1. 可视化 Workflow 编辑（节点拖拽、连线、参数配置、保存/加载）
2. 六类节点：Start / Agent / Condition / Tool / Loop / End
3. 顺序执行与条件二路分支（true/false 标签边）、循环执行
4. Run 级状态持久化（PostgreSQL）与实时监控（SSE 事件流）
5. Agent 经 OpenAI 兼容协议调用大模型（默认 DeepSeek），Tool 系统提供文件、Shell、Git、HTTP、搜索、沙箱等能力
6. Coding Agent（OpenCode）在 Docker 沙箱中读写代码、执行测试
7. 自举开发：Git worktree 隔离 → 编码 → 测试/审查循环 → 合并 main → 自动重建部署

## 3. 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Vue Flow + Pinia | Vue Flow 负责画布交互；状态与视图分离，无重型 UI 组件库 |
| API | Fastify 5 | 原生 ES Module、内建 JSON Schema 校验 |
| Workflow Runtime | **自研**（非 LangGraph） | DSL→编译→解释执行的完整链路自持（见 §4）；不依赖外部图运行时，控制流、事件、持久化语义完全可控 |
| 数据库 | PostgreSQL + pg | 表：workflows / workflow_runs / node_runs / workflow_states / checkpoints / workflow_jobs |
| 队列 | PostgreSQL `workflow_jobs` 表（SKIP LOCKED 抢占） | 不引入 Redis：单库事务保证 Run 与 Job 一致性，重试/超时/锁定语义在 SQL 层实现 |
| 大模型 | OpenAI 兼容协议（DeepSeek） | `openai-compatible-provider.ts` 统一接入，模型名经配置注入 |
| Coding Agent | OpenCode（CLI，`--format json` 事件流） | 经 Adapter 解耦，本地进程与 Docker 沙箱两种执行模式 |
| 沙箱 | Docker（`ai-workflow-sandbox:latest` 镜像） | 见 §7 |
| 进程管理 | pm2 | 后端常驻；前端为静态产物由 Nginx 托管 |

## 4. Workflow Runtime（自研）

### 4.1 三层分离

```text
Workflow Definition（DSL）   描述工作流是什么
        │ validate（共享类型包 workflow-validator，JSON Schema 校验）
        ▼
Runtime 编译装配            拓扑分层、出边映射、参数绑定
        │ （后端 workflow/runtime）
        ▼
Workflow Run                一次执行及其状态
（nodeRuns / variables / iterations / checkpoints / events）
```

Definition 与 Run 严格分离：Definition 只读可复用，Run 记录每次执行的节点状态、输入输出、Token 用量与迭代计数。

### 4.2 执行模型

- **调度**：Runtime 按拓扑分层推进；Condition 节点求值后选择 `true`/`false` 标签出边（参数+关系配置或表达式求值）；Loop 节点按 body 分支反复执行，受 `maxIterations` 与停止条件约束。
- **控制权归属**：节点调度、分支选择、迭代上限、超时、重试、状态持久化全部由 Runtime 决定；LLM 只在 Agent 节点内做推理与业务判断，绝不决定流程走向。
- **事件**：Runtime 对外发射 `NODE_STARTED / NODE_COMPLETED / NODE_FAILED / LOOP_STARTED / LOOP_ITERATION / LOOP_CONTINUED / RUN_COMPLETED / RUN_FAILED / RUN_CANCELLED` 事件。事件是平台的核心观测通道：
  - 前端 Run 监控经 SSE 实时渲染；
  - 自举开发的进度 Map 由 `eventSink` 驱动（见 §8.3）。
- **持久化**：Run 完成后落库（含 checkpoint）；DB 不可用时降级内存模式并在响应中标记。

### 4.3 Loop Engineering

Loop 是 Runtime 原语：`iteration` 计数、`maxIterations` 硬上限、条件停止、节点级重试与超时、状态持久化、取消传播。测试/审查/修复的「观察-验证-决策-再执行」循环由普通 Condition + Loop 节点组合表达，无任何特殊分支。

## 5. Agent 与 Tool 系统

### 5.1 Agent

- `AgentRegistry` 按 `executorId` 注册执行器；普通 Agent 节点走 `agent-executor`（构建 Prompt → 调用模型 → 解析结构化输出 `{ goals, tasks, passed, ... }`）。
- 输出参数契约：Agent 节点声明输出 Schema（如文本输出的 `text: String`），下游节点经**参数继承**从上游节点的输出中选择输入（前端下拉级联：上游节点 → 其输出参数），避免手工填写易错的变量名。
- 模型 Provider：OpenAI 兼容协议；默认模型 `deepseek-chat`，可按节点覆盖。

### 5.2 Tool

Tool 实现统一 `Tool` 接口（输入 Schema + execute），注册于 `ToolRegistry`：

| Tool | 说明 | 安全约束 |
|---|---|---|
| file / workspace | 读写工作区文件 | 路径必须解析到 workspace 根内（boundary 检查），大小上限 |
| shell | 执行命令 | **无 shell 解释**（spawn 直调）、运算符 `;&\|<>$()` 拒绝、命令白名单（读/写文件常用命令） |
| git | 分支/提交/diff | 固定子命令集 |
| http | HTTP 请求 | URL 校验、超时 |
| search | 工作区内容搜索 | workspace 边界 |
| sandbox | Docker 沙箱内执行命令 | 见 §7 |

错误统一为 `{ code, message }`（`INVALID_INPUT` / `WORKSPACE_BOUNDARY` / `SANDBOX_ERROR` 等），映射到 HTTP 400/403/422。

## 6. 数据与持久化

```text
workflows        Workflow 定义（JSONB）
workflow_runs    Run 头（状态/时间/错误/Token 汇总）
node_runs        每节点执行记录（输入输出 JSONB、迭代号、attempts）
workflow_states  Run 级变量快照
checkpoints      循环/断点状态（可恢复）
workflow_jobs    异步任务队列（status/attempts/max_attempts/available_at/locked_by/locked_until）
```

队列语义（`queue/jobs/postgres.ts`）：`FOR UPDATE SKIP LOCKED` 抢占、`available_at` 延迟重试、`locked_until` 死锁回收、`max_attempts` 上限——全部 SQL 原生实现，无外部队列依赖。

## 7. 沙箱（Docker）

Coding Agent 与代码执行命令运行在一次性容器中：

```text
docker run --rm --init
  --mount type=bind,source=<workspace>,target=/workspace   # 工作区挂载
  --cpus 1 --memory 1536m --pids-limit 256                 # 资源上限
  --cap-drop ALL --security-opt no-new-privileges          # 权限收敛
  --read-only                                              # 根文件系统只读
  --tmpfs /tmp:rw,noexec,nosuid,size=512m                  # 进程可写区
  --tmpfs /var/cache/npm:rw,noexec,nosuid,size=512m        # npm 缓存独立挂载
  -e npm_config_cache=/var/cache/npm
  [--network none | 网络开启]                                # 网络访问开关
```

设计要点（均来自生产事故复盘）：

1. **npm 缓存与 opencode 存储隔离**：opencode 的 SQLite 会话存储在 `/tmp`，若 npm 缓存同区会将其写满导致 `Failed to execute statement`。独立 tmpfs 后互不挤占。
2. **内存上限**：容器内存须容纳 npm install + opencode 同驻（1536m / 宿主 3.6G），过低会被 cgroup OOM 杀死（exitCode=137）。
3. **失败原因透传**：容器非零退出时，errorMessage 携带 `exitCode` 与 stderr 尾部 5 行，端到端可见，避免「Sandbox 执行失败」这类无信息报错。
4. **输出上限**：coding agent JSON 事件流含文件内容，上限须设 8MB（默认 256KB 必失败）。

镜像 `ai-workflow-sandbox:latest`：node24-bookworm-slim + git + opencode，Dockerfile 位于 `后端/docker/sandbox.Dockerfile`。

## 8. 自举开发（Self-Development）

### 8.1 拓扑

自举工作流是**普通 Workflow**，无任何特判分支：

```text
start → requirement-analyzer（需求分析）
      → task-decomposer（任务拆解）
      → coding-agent（沙箱内编码，OpenCode）
      → loop:
           test-agent（运行相关测试）
           reviewer（审查 diff/测试/架构）
           condition（通过？）
             ├── 通过 → commit-1（git 提交合并）
             └── 未过 → fix-agent（修复）→ 回到 loop
      → end
```

### 8.2 会话与隔离

- 每次任务创建一个会话：`git worktree add -b agent/<taskId>` 于 `后端/.ai-workflow-workspaces/`，与主检出完全隔离。
- 合并前检查基础仓库 clean（`BASE_WORKTREE_DIRTY` 拒绝合并）——运行时数据（`后端/data/`、`.ai-workflow-workspaces/`）全部 untrack，工作环境内的用户编辑不可能污染合并。
- 会话记录（session.json / result.json）落在 workspaces 目录，服务重启后 `restore()` 恢复。

### 8.3 实时进度

`DevelopmentSessionManager` 维护内存进度 Map，由 Runtime 事件流驱动（`RUNNING / SUCCESS / FAILED / MERGING / MERGED / MERGE_FAILED` 八相位 + 每节点状态 + 循环轮次）。前端 1.5s 轮询 progress 端点；会话列表接口返回 `phase`，运行中的会话显示在执行状态区而不进入已完成列表，页面重挂载自动恢复轮询。

### 8.4 响应瘦身

Run 原始结果可达数 MB（checkpoints、节点输入链、agent 原始事件流）。HTTP 边界统一经 `compact.ts` 瘦身（`后端/src/self-development/compact.ts`）：

- 剔除 `checkpoints`、`variables`、节点 `input`、`rawOutput`；
- `events` 仅保留前端渲染「执行过程」所需字段，文本截断；
- 超过 16KB 的其他字段截断标注。

完整数据保留在内存与 result.json 中，会话详情响应从 3.5~8MB 降到 ~15KB。

### 8.5 自动部署

merge 成功后 orchestrator 触发 `onMerged` → app 层 **detached spawn** `scripts/deploy-after-merge.sh`（`SELF_DEVELOPMENT_AUTO_DEPLOY=true` 启用）：

```text
flock 串行 → 对 HEAD^1..HEAD 的 diff 按目录判定改动范围
  （改前端 → 重建 dist + dist-root 两个 bundle；
   改后端/共享类型 → 重建 shared-types + 后端）
→ git add -f dist 产物并提交（保持仓库 clean，不阻塞下次合并）
→ pm2 restart
```

两个实现细节：脚本路径须用 merge 结果里 `git rev-parse --show-toplevel` 的真实仓库根（进程启动目录可能是仓库内子目录）；diff 须带 `-c core.quotepath=false`（中文顶层目录默认八进制转义，改动检测会漏判）。日志：`/www/wwwlogs/ai-workflow-autodeploy.log`。

## 9. 前端设计

四个主视图（单页内切换）：

| 视图 | 职责 |
|---|---|
| 编辑器 | Vue Flow 画布：左侧节点面板（拖入新增）、节点配置（模型/系统提示/参数继承级联）、连线校验、本地自动保存 + 服务端保存、4 个内置 Demo 工作流 |
| 运行监控 | Run 列表 / Run 详情（状态、Token 汇总、节点执行、SSE 实时日志） |
| 工作环境 | Workspace 文件树（按父目录分组缩进）、文件在线编辑、目录/文件增删；demo 输入由后端启动时补种 |
| 自举开发 | 需求输入 → 实时进度（相位/节点/轮次）→ 执行结果 → Diff → 会话列表（按发起时间降序） |

约定：

- **展示时间统一东八区**（`前端/src/utils/datetime.ts`，`Asia/Shanghai`），存储保持 ISO/UTC，只在展示层转换。
- 部署双 bundle：IP 子路径版（`VITE_BASE=/ai-workflow/`）与域名根路径版（`VITE_BASE=/`）。
- UI 组件库未引入重量级依赖，样式集中于 `styles.css`。

## 10. 安全设计

1. **访问控制**：全 API 邀请码门禁（`INVITE_CODE`，header `x-invite-code` 或 query），前端首次进入校验并本地存储。
2. **密钥管理**：`.env` 全程 untrack（`git rm --cached`），不进仓库、不进合并历史；DeepSeek key 仅经环境变量注入沙箱容器。
3. **Shell 注入**：无 shell 解释层 + 字符白名单 + 命令白名单三重防线。
4. **路径逃逸**：所有文件工具先 `realpath` 再校验必须位于 workspace 根内。
5. **沙箱容器**：只读根、cap-drop ALL、no-new-privileges、noexec tmpfs、资源与 PID 上限、网络默认可关。

## 12. 关键设计决策记录

| 决策 | 背景 | 选择 |
|---|---|---|
| 自研 Runtime 而非 LangGraph | 需要事件流、八相位自举进度、响应瘦身等深度定制 | 完整自持 DSL→编译→执行链路，控制流不外委 |
| PostgreSQL 队列而非 Redis/BullMQ | 单库即可保证 Run/Job 事务一致 | `workflow_jobs` 表 + SKIP LOCKED |
| HTTP 边界响应瘦身 | 会话详情 3.5~8MB 导致前端卡死 | compact 层：传输 KB 级，完整数据留在服务端 |
| 沙箱 tmpfs 分区 + npm 缓存独立挂载 | npm 缓存写满 /tmp 击穿 opencode SQLite | 两块 512m tmpfs，npm 指向专用挂载 |
| merge 后自动部署 | agent 产物 base 配置不可信、手动重建易遗漏 | 平台侧权威重建：范围检测 + flock + detached |
| 展示层时区统一 | 后端 UTC、用户在东八区，原始 ISO 展示差 8 小时 | 前端统一 formatter，存储不动 |
| 运行时数据 untrack | 工作环境编辑会弄脏仓库阻塞合并 | `后端/data/`、workspaces 全 untrack + 启动补种 demo 输入 |
